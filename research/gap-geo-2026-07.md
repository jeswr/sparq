## 1. Corpus

The **fixed CRS84 point corpus** generated by `bench/geo/gen.sh 100000`:
`/tmp/geo/points-100000.nt` (seed 20260615, 8°×8° France-ish window,
~100 000 `geo:asWKT` POINT literals). The corpus is deterministic and byte-identical
across all runs of the same binary; it is the same substrate the per-commit
`bench/geo/run.sh` gate asserts. The expected count oracle is `bench/geo/expected.tsv`.

---

## 2. Harness (`scripts/bench/geo-same-box.sh`)

Built on the `scripts/bench/shacl-same-box.sh` template. Emits one
`canonical-competitor-results`-shaped envelope JSON so a future canonical gather
is ingestible by `scripts/bench/ingest-canonical-competitors.mjs` unchanged.

### 2.1 sparq leg (in-process)

`bench/geo/run.sh` invokes `examples/bench_geo` in `bench` mode: loads the corpus
once, builds the spatial index, then runs best-of-N per workload. Every count is
**hard-asserted against `bench/geo/expected.tsv`** before the timing is emitted.
A count drift exits the harness with `SPARQ_STATUS=failed`.

### 2.2 jena-geosparql leg (HTTP)

jena-fuseki-geosparql (standalone Maven jar, default version 5.4.0) is started with
the same corpus loaded into an in-memory dataset. Each workload's pinned query
(`bench/geo/queries-jena/<workload>.rq`) is POSTed via
`scripts/bench-adapters/http_sparql_adapter.py` (best-of-N, `--json` sidecar for
result parsing). `query_us` includes the full HTTP round-trip: TCP connect, HTTP
framing, and SPARQL-JSON parse — a **recorded mode asymmetry** vs sparq's in-process
index surface, never adjusted away.

Download is controlled by `GEO_FETCH_JENA=1` (default). If java is absent or the jar
fails to start, the jena leg is **gracefully skipped**: the envelope records the reason
and the script still exits 0. A skip is a missing column and a re-run action, never a
sparq win (protocol point 6 of §4 in
`research/comparative-benchmarking-everything.md`).

### 2.3 Workloads

| workload | description |
|---|---|
| `within10km` | COUNT of corpus points within 10 km great-circle of POINT(0 51) |
| `within50km` | COUNT of corpus points within 50 km great-circle of POINT(0 51) |
| `nearest_k10` | 10 nearest points to POINT(0 51) by geof:distance (ORDER BY + LIMIT 10) |
| `nearest_k100` | 100 nearest points (ORDER BY + LIMIT 100) |
| `geof_within` | COUNT of points satisfying geof:sfWithin(point, 1°×1° box at (0,51)) |

`geo_compliance_pass` (the OGC fixture ratchet) is sparq-only and is **not** a
competitor row: replaying the OGC topology fixture set against Jena is out of scope.

## 3. INVARIANT: counts-not-coordinates

**No timing without result-set-size agreement per query.**

Float geometry is not bit-stable, so only result-set SIZES are cross-checked — never
coordinate values. sparq counts are additionally hard-gated vs `bench/geo/expected.tsv`
by `run.sh`. A **count disagreement is itself a recorded result** (both counts kept in
`count_crosscheck`, the timing withheld). Disagreement is plausible on the radius
workloads because sparq `within*` uses **spherical great-circle** distance while
Jena / Apache SIS `geof:distance` uses **ellipsoidal geodesic** — radius-boundary
membership can legitimately differ at the margin.

## 4. Mode asymmetry (load-bearing, not adjusted)

| property | sparq | jena-geosparql |
|---|---|---|
| measurement surface | in-process (`bench_geo`, index API) | HTTP SPARQL (jena-fuseki-geosparql) |
| timing scope | load + index once, best-of-N query | full HTTP round-trip (connect + SPARQL-JSON parse) |
| HTTP overhead | none | ~a few hundred µs floor (localhost) |

This asymmetry is recorded in every envelope and is **never adjusted**: sparq-geo is not
wired into sparq-server, so a symmetric HTTP-vs-HTTP row is not currently possible. The
correct interpretation is that any observed sparq in-process lead is a **floor** — the
gap vs a sparq HTTP surface would be smaller, and the harness notes this.

## 5. Query translations (`bench/geo/queries-jena/`)

Five pinned `.rq` files, one per workload. The within/geof_within queries are verbatim
copies of the sparq-native files in `bench/geo/queries/` — no translation needed, as
standard GeoSPARQL dialect (PREFIX `geo:`, `geof:distance`, `geof:sfWithin`, `uom:metre`)
is supported identically by Jena.

The **nearest_k** queries differ: sparq evaluates k-nearest via the
`GeoIndex::nearest` index surface; standard GeoSPARQL has no k-nearest function.
The pinned Jena rendering uses `ORDER BY ASC(geof:distance(...)) LIMIT k`, which is
the standard-visible form that any engine is free to optimise internally. Jena's
non-standard `spatial:nearby` function requires a bounding radius and is NOT a faithful
k-NN rendering; it is not used. The only cross-checked value for these workloads is the
result-set SIZE (== k on a corpus larger than k), never the ordering or the exact points
returned.

Honest findings, for the consolidation bead `sq-hmd7l.27`:

1. **`within*` crosscheck is RED — jena returned 0 hits on both radius workloads.**
   Zero (vs sparq's 51/1547) is NOT the documented spherical-vs-ellipsoidal
   boundary-margin effect (§3) — that would move a handful of edge points, not all
   of them. This looks like a translation/units semantic gap in the pinned jena
   rendering of the `geof:distance ≤ radius` filter (jena executed the query fine:
   0 hits in ~0.61 s). Per the invariant the jena timings are withheld and NO
   comparative verdict is drawn. Harness root-cause bead filed (see §6c).
2. **`nearest_k*` CLEARLY-AHEAD carries two caveats** (recorded in the envelope,
   never adjusted): (a) mode asymmetry — jena is a full HTTP SPARQL round-trip vs
   sparq's in-process index surface (the HTTP floor is negligible at the observed
   1.5 s scale); (b) the jena rendering is the standard-visible
   `ORDER BY ASC(geof:distance(...)) LIMIT k` full scan-and-sort, since standard
   GeoSPARQL has no k-NN function — any engine is free to optimise it, jena does not.
3. **`geof_within` is AHEAD-BUT-NOT-OOM (~1.5×) — a dominance-mandate gap row.**
   sparq's own 90.5 ms is ~600× slower than its `within50km` (150 µs) on the same
   corpus for a similar-cardinality result (1526 vs 1547) — root-cause hypothesis:
   the `geof:sfWithin` FILTER path evaluates as a full scan (per-point WKT
   parse/geometry test) instead of using the spatial index that serves `within*`.
   Engine-side profiling-first fix bead to be filed by `sq-hmd7l.27`.

## 8. PostGIS (excluded per registry caveat)

PostGIS is a SQL-native spatial store, not a SPARQL triplestore. It is listed in
`bench/competitors.json` with a `loose_lower_bound` role caveat: it is included
**only** with matched CRS/operation semantics. The geo workloads use WKT + GeoSPARQL
functions (`geof:distance`, `geof:sfWithin`) with CRS84 / EPSG:4326 coordinates.
PostGIS supports equivalent operations (`ST_Distance(geography,...)`,
`ST_Within(...)`), but the CRS and function-semantic mapping (spherical vs ellipsoidal
for `ST_Distance(geography,...)` vs `ST_Distance(geometry,...)`) requires per-query
verification. Until that verification is done and the PostGIS-side query translations
are pinned, PostGIS is **omitted** from this harness — consistent with the registry
caveat and the counts-not-coordinates invariant.
