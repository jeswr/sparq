# RSP competitor gap — July 2026

Part of the comparative-benchmarking-everything program
(`research/comparative-benchmarking-everything.md` §5.2, epic sq-hmd7l). This is the
**first-read** record for the bounded count-matched-replay RSP comparison; everything
here was gathered on the shared work box and is **NON-canonical** (counts are
deterministic and machine-independent; timing is trend-only until re-gathered on the
quiet EC2 reference box).

## The protocol (implemented, sq-hmd7l.20)

`bench/CATALOG.md` previously ruled an RSP throughput head-to-head apples-to-oranges
outright. The design record §5.2 replaces that with the **bounded** protocol, now
implemented in `bench/rsp/`:

1. **Identical replay** — the oracle's fixed `(triple, ts)` scripts are exported as
   pinned files (`bench/rsp/replay/*.ts.tsv`, sha256 in every envelope). A
   **fidelity guard** (`test_rsp4j_compare.py`) re-derives every scenario's
   per-window counts from the files and asserts them against `bench/rsp/expected.tsv`
   (which `run.sh` pins to the in-code scripts). The guard is count-structural: a
   literal-value-only edit that changes no count is not observable at this level.
2. **Count-match FIRST** — `bench/rsp/rsp4j_compare.py count-match` requires
   per-window result-count agreement with the deterministic oracle before admitting
   ANY timing row. Windows that cannot be count-matched are excluded and the
   exclusion is reported (`excluded_windows` / `leading_partial_reports` /
   `conflicting_reports` in the envelope); a corrupted or disagreeing count stream
   yields verdict `NOT-COUNT-MATCHED`, zero rows, exit 3.
3. **Machine-attached caveat** — every emitted comparison row carries
   `time_model_caveat: true` plus the caveat text; it travels in the envelope, not
   just prose.

## Engine leg: RSP4J/YASPER (verified, not just sketched)

`bench/rsp/rsp4j/Rsp4jReplayRunner.java` + `gather-rsp4j.sh` drive **RSP4J's YASPER**
(operator API, `TPQueryFactory` RSP-QL dialect) in its **event-time** configuration —
`DataStream.put(graph, ts)` with the replay's own timestamps, no wall clock. Pinned
build: `streamreasoning/rsp4j` @ `c46e0f674` (jar 1.0.1, Apache-2.0), built locally
at gather time (never a committed dependency). Note the registry's original
`riccardotommasini/rsp4j` URL now 404s — the repo moved to the `streamreasoning` org
(registry-fix bead sq-6wx83).

Protocol details verified against the RSP4J sources and declared in every envelope:

- **Boundary heartbeats**: YASPER's C-SPARQL S2R reports `OnWindowClose` strictly
  (`w.getC() < t_e`) and only on element arrival, so the driver pushes a dummy
  heartbeat graph (predicate matching no query pattern) to every stream at each
  window boundary + 1; the shared `TimeImpl` suppresses duplicate same-ts
  evaluations across streams.
- **Time scale**: the RSP-QL dialect parses whole-second durations only, so replay
  timestamps are scaled ×1000 (order/spacing unchanged — the same replay).
- **Missing-report-as-zero**: an RSTREAM of an empty relation emits nothing; an
  expected-but-silent window is scored 0 under a declared, envelope-recorded policy.
- **Leading partial windows**: C-SPARQL's SECRET scope opens windows before t0;
  the oracle's sequence starts at k = 0, so k < 0 reports are protocol exclusions,
  reported not hidden.

## Count-comparable surface (honest)

YASPER's TP dialect has **no GROUP BY / SUM / AVG**, so only scenarios whose
per-window row count is a distinct-binding count are count-comparable today:

| scenario | verdict |
|---|---|
| `srbench_join` (multi-window obs ⋈ station-metadata, SELECT of all pattern vars) | **COUNT-MATCHED** — 4/4 windows agree with the oracle (w0–w2 exact, w3 via the declared missing-as-zero policy); envelope: `bench/canonical-competitor-results/2026-07-11/rsp4j-yasper-count-match-*.json` |
| `tumbling_avg`, `sliding_sum`, `tumbling_groupby_join`, `srbench_groupby_state` | **NOT-COUNT-COMPARABLE-IN-DIALECT** — aggregate row-count semantics not expressible in YASPER's TP dialect; excluded and reported per §5.2 (widening bead sq-rpdae: RSP4J's csparql2 module carries a full-SPARQL/Jena R2R) |

**Precision correction (sq-rpdae).** "No GROUP BY / SUM / AVG" above is right in effect but
imprecise in mechanism. Re-read against the pinned sources: `TPVisitorImpl.visitSelectQuery`
*does* parse a projection aggregate `(FUNC(?v) AS ?out)` into an `Aggregation`, the operator
API *does* have an evaluation path for it (`QueryTaskOperatorAPIImpl` → `aggregate(...)`), and
the dialect also carries a simple per-window `FILTER` and a default-graph clause. What it has
**nowhere** is a **`GROUP BY`** — no grouping key exists anywhere in the dialect — so the three
per-group scenarios (`sliding_sum` one row per sensor, `tumbling_groupby_join` one row per room,
`srbench_groupby_state` one row per state) remain inexpressible. The single-group `tumbling_avg`
*is* in-dialect syntactically; driven through the existing runner it emitted **zero reports**, so
it does not become count-comparable either. Net effect on the surface: unchanged.

## Throughput verdict: still NOT-MEASURED — harness now exists (sq-3f5ay)

The gate admitted the runner's replay-push timing rows (they count-matched), but the
pinned oracle replay is tiny (19 events) — a sustained-rate claim off it would be
meaningless, and sparq's advisory `rsp_persistentdict_triples_per_s` comes from a
*different* synthetic workload, so no side-by-side sustained-throughput row is
published. Verdict for the throughput axis: **NOT-MEASURED**.

**sq-3f5ay built the matched-workload harness; it did not (yet) produce the
measurement.** What now exists and is verified:

- **The sparq-side replay-FILE runner** — `crates/sparq-rsp/examples/replay_runner.rs`.
  Until it existed there was no way to drive sparq-rsp from the same file RSP4J's Java
  runner reads, which is the whole reason the two engines' numbers came from different
  workloads. Verified equivalent to the in-code oracle: `bench/rsp/run.sh` re-derives all
  five scenarios' per-window counts through the file path and asserts them against
  `expected.tsv` (21 counts), and that guard is non-vacuous — deleting one event from a
  committed replay export makes it red while the in-code oracle path stays green.
- **A pinned SCALED replay** — `srbench_join`-shaped at 100-sensor scale (10⁵-event
  order). The payload is not committed; the pin is the deterministic generator
  (`rsp4j_compare.py gen-replay`) plus `bench/rsp/replay/scaled.manifest.json`
  (parameters + sha256). Regeneration is byte-reproducible; a drifted parameter is
  refused against the pinned sha rather than silently comparing two workloads.
- **The both-engines path** — `SCALED=1 bench/rsp/gather-rsp4j.sh`, and
  `count-match --oracle-runner`, which sources the oracle side from the sparq runner
  (a scaled replay has no `expected.tsv` entry) and puts BOTH engines' sustained
  triples/s into `rows`, engine-labelled, each carrying the machine-attached caveat.

**Shape correction to the bead's premise.** The bead proposed reusing the throughput
example's single-stream 100-sensor `AVG` shape. That shape is not count-comparable in
YASPER's dialect, and the INVARIANT admits no throughput row for windows that cannot be
count-matched — so a scaled `AVG` replay could never have produced a publishable row. The
scaled replay keeps the 100-sensor scale but uses the `srbench_join` shape, the only
count-comparable scenario on this surface.

**Why the verdict does not move yet.** The RSP4J/YASPER leg over the scaled replay is
gather-time — it needs a JDK, maven and network to build `streamreasoning/rsp4j` at the
pinned commit — and has **not been run**. The sparq side measures on the shared work box
(non-canonical, trend-only). With no competitor number over the same file, there is no
side-by-side, so the throughput axis stays **NOT-MEASURED** until a gather run writes the
envelope. The remaining work is an *execution* step, not a design or implementation one.

One risk that gather run will surface, recorded now rather than discovered later:
`srbench_join` over the scaled replay yields ~10³ join rows per window over ~10² windows,
where the tiny oracle replay yields 0–3. YASPER's per-window materialisation and the
driver's set-per-report-ts dedup are untested at that size; if the count-match fails or
the run does not complete, the honest outcome is a *reported exclusion* under the existing
protocol, not a quietly shrunk replay. The manifest's parameters are the knob to
re-pin if so — but a re-pin changes the workload and must be stated as such.

## csparql2 full-SPARQL R2R evaluation (sq-rpdae) — VERDICT: does NOT widen the surface

RSP4J's `csparql2` module carries `R2ROperatorSPARQL` — Jena ARQ running **full SPARQL**
(aggregates, `GROUP BY`, `FILTER`, static `FROM` graphs) over an Esper-materialised SDS —
so sq-rpdae asked whether driving it with the **same pinned replay** widens the
count-comparable surface beyond `srbench_join`. It does not. Evaluated 2026-07-26 against
`streamreasoning/rsp4j` @ `c46e0f674` (csparql2 module version **2.0.0** — *not* the 1.0.1
the api/yasper/operatorapi modules carry), Esper 7.1.0, on the shared work box;
counts below are deterministic and machine-independent. Reproduction:
`bench/rsp/gather-csparql2.sh` + `bench/rsp/rsp4j/Csparql2ReplayRunner.java`.

**1. Blocking defect — csparql2 self-deadlocks under an externally driven clock.**
`EsperGGWindowOperator.EsperGGWindowAssigner.getContent()` calls `statement.safeIterator()`
and never `close()`s it, leaking the Esper statement's `ReentrantReadWriteLock` **read**
lock on the first window materialisation. The next `CurrentTimeEvent` (how the driver
advances event time) needs the **write** lock on that same thread and parks forever — the
runner **hangs**, it does not fail. Confirmed by thread dump (`EsperTime.setAppTime` →
`EPRuntimeImpl.processStatementScheduleMultiple` → `acquireWriteLock` → parked) and removed
by a one-line `finally { iterator.close(); }`. The gather script applies that patch
**explicitly** and records it in the envelope `version` string; nothing here is measured
against unpatched upstream. **Not yet reported upstream** — captured as a follow-up.

**2. Multi-window scenarios emit ZERO rows.** With the patch applied, `srbench_join` and
`srbench_groupby_state` produced no output under **three** flag combinations each — default,
`--non-empty-content false`, and `--ts-offset 1 --non-empty-content false` (six runs). The
two named windows report at
**different** event times (`wm` at 10000/20000/30001/40001/50001, `wo` at
12000/21000/35000/50001), so no synchronized two-window snapshot ever exists when the R2R
operator runs and the join never yields a solution. **NOT-COUNT-COMPARABLE** — and note this
is strictly worse than YASPER, which count-matches `srbench_join` 4/4.

**3. Single-window aggregates run, but their agreement is not admissible.** Under
`--ts-offset 1 --non-empty-content false` the existing gate scores:

| scenario | gate | note |
|---|---|---|
| `tumbling_avg` | 5/5 COUNT-MATCHED | needs `non_empty_content=false`, else the empty window [10,20) reports nothing while the oracle emits one AVG row |
| `sliding_sum` | 5/5 COUNT-MATCHED | — |
| `tumbling_groupby_join` | **NOT-COUNT-MATCHED** | w0 = 1 vs oracle 2 |

The two matches are **window-alignment-contingent and must not be promoted to the published
comparable surface.** csparql2's S2R is an Esper **sliding** `win:time` snapshotted at
whatever external-clock value the driver advanced to when it crossed the boundary —
`(T-range, T]` — *not* the oracle's aligned `[k*step, k*step+range)`. `tumbling_groupby_join`
is the witness: its w0 loses the `<http://ex/in>` room triple at the window's left edge
(ts 0), which has already expired by snapshot time, so one room is counted instead of two.
The two "matching" scenarios are not evidence against that misalignment — they are **silent**
about it. On this replay exactly one event falls inside the clipped edge: the triple at
ts 0, which is an `<http://ex/in>` **room** triple. `tumbling_groupby_join` is the only
scenario that reads it, which is precisely why it is the only one that diverges;
`tumbling_avg` and `sliding_sum` match on nothing but value triples, none of which sit in
the clipped region, so their windows are never actually perturbed. Their agreement therefore
says nothing about whether the window semantics coincide — a replay with a value triple at a
window's left edge would be the real test, and no such replay exists today. Landing the
heartbeat exactly on the boundary
instead of boundary+1 does not fix it — reporting then drifts to element-arrival times
(20000, 21001, 31001, 41001), which is worse. Exact alignment is not reachable from the
driver side.

Because a passing count-match here would otherwise read as a widened surface, the caveat is
**machine-attached, not prose**: `rsp4j_compare.py --protocol-caveat` puts it in the envelope
*and* on every emitted row, the same discipline `time_model_caveat` already follows.

**Surface after sq-rpdae: unchanged — `srbench_join` (YASPER) only.** Reopening the aggregate
scenarios needs an engine whose S2R window is boundary-aligned, or a csparql2 fix for both the
deadlock and the multi-window synchronisation; neither is in this bead's scope.

## CityBench mapping note (sq-rpdae)

Promised by the sq-hmd7l.20 bead text: which CityBench queries can be count-matched under
which dialect. Grounded in the **11 pinned RSP-QL query files** that ship in the RSP4J tree
at `c46e0f674` (`csparql2/src/test/resources/citybench/`: q1–q8, q10–q12; **q9 is absent
upstream**), read directly rather than from the paper.

| query | windows | needs beyond plain BGP | YASPER TP dialect | csparql2 full SPARQL |
|---|---|---|---|---|
| q1 | 2 | static `FROM` graph | ✗ 2-window + static | ✗ multi-window desync |
| q2 | 2 | static `FROM` | ✗ | ✗ multi-window desync |
| q3 | 2 | static `FROM`, projection expr `((?v1+?v3)/2)` | ✗ no projection expressions | ✗ multi-window desync |
| q4 | 1 | 2 static graphs, arithmetic `FILTER` | ✗ FILTER is relational-only, no arithmetic | ~ single-window, alignment caveat |
| q5 | 1 | 2 static, arithmetic `FILTER`, projection expr | ✗ | ~ single-window, alignment caveat |
| q6 | 2 | static `FROM` | ✗ | ✗ multi-window desync |
| q7 | 2 | static `FROM`, disjunctive `FILTER` | ✗ 2-window | ✗ multi-window desync |
| q8 | 2 | 2 static, disjunctive `FILTER` | ✗ | ✗ multi-window desync |
| q10 | 2 | static `FROM` | ✗ | ✗ multi-window desync |
| **q11** | **1** | none — `SELECT *`, single window, plain BGP | **~ in-dialect** | ~ single-window, alignment caveat |
| q12 | 1 | static `FROM`, `FILTER`, `GROUP BY`, `HAVING(count(...))` | ✗ no GROUP BY/HAVING | ~ single-window, alignment caveat |

Reading: **`q11` is the only CityBench query that is even syntactically in-dialect for
YASPER** — every other one needs at least one of {second window with a cross-window join, a
static `FROM` graph in the default graph, an arithmetic or disjunctive `FILTER`, a projection
expression, `GROUP BY`/`HAVING`}. Under csparql2 all 11 are *expressible*, but the seven
two-window queries are blocked outright by finding 2 above, and the four single-window ones
(q4, q5, q11, q12) inherit the alignment caveat of finding 3 — so none of them is
count-matchable **today** on the same terms as `srbench_join`.

Two prerequisites before any CityBench window can be count-matched at all, independent of
dialect:

1. **The data is not pinned anywhere.** The queries dereference `<http://citybench/SensorRepository.rdf>`,
   `<http://citybench/AarhusCulturalEvents.rdf>` and `<http://citybench/AarhusLibraryEvents.rdf>`
   by IRI at registration, and the Aarhus traffic/pollution/parking/weather streams are not in
   this repo or in RSP4J. A count-matched CityBench leg needs those files pinned locally with
   sha256s first, exactly like `bench/rsp/replay/*.ts.tsv`.
2. **sparq needs the oracle side.** `sparq-rsp` would have to express the static-graph +
   `FILTER` + `HAVING` surface these queries use and emit deterministic per-window counts for
   them, which is a `sparq-rsp` crate task, not a bench task.

Net: CityBench stays **NOT-COUNT-MATCHED (not attempted)**. The cheapest first step, if it is
ever picked up, is **q11 against YASPER** — one window, plain BGP, `SELECT *`, no static graph
— which is the only cell in the table that needs neither a new dialect capability nor the
alignment fix.
