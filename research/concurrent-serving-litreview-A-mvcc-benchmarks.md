# Topic A — Isolation & concurrency control for a read-mostly RDF store

## A.1 MVCC / snapshot isolation fundamentals; SSI and write skew

**Snapshot isolation (SI).** Each transaction reads from a committed snapshot taken at start; writers conflict only on write-write overlap (first-committer-wins). Reads never block writes and vice versa. SI's known anomaly is **write skew**: two concurrent transactions each read an invariant-relevant item the other writes (classic doctors-on-call example), producing a non-serializable result ([Cahill et al., SIGMOD 2008](https://dl.acm.org/doi/10.1145/1376616.1376690); [PDF](https://people.eecs.berkeley.edu/~kubitron/courses/cs262a-F13/handouts/papers/p729-cahill.pdf); [Wikipedia: Snapshot isolation](https://en.wikipedia.org/wiki/Snapshot_isolation)).

**SSI (Cahill, Röhm, Fekete, SIGMOD 2008).** Key theorem (building on Fekete et al. 2005): every SI anomaly contains a "dangerous structure" — a *pivot* transaction with both an incoming and an outgoing rw-antidependency to concurrent transactions. SSI tracks reads via SIREAD locks and per-transaction `inConflict`/`outConflict` flags and aborts one transaction whenever a pivot forms (conservative: false positives possible, no false negatives). Implementation in Berkeley DB took ~700 modified lines out of >200,000; on SmallBank SSI performed "close to plain SI and significantly better than 2PL under contention" ([summary](http://muratbuffalo.blogspot.com/2025/07/serializable-isolation-for-snapshot.html)). Phantom handling: [Cahill's thesis](https://ses.library.usyd.edu.au/bitstream/handle/2123/5353/michael-cahill-2009-thesis.pdf).

**PostgreSQL SSI (Ports & Grittner, VLDB 2012)** — first production SSI, PostgreSQL 9.1 ([paper](https://www.drkp.net/papers/ssi-vldb12.pdf); [arXiv 1208.4179](https://arxiv.org/abs/1208.4179); [PostgreSQL wiki](https://wiki.postgresql.org/wiki/Serializable)). Quantitative:
- SIBENCH: 10–20% overhead vs plain SI without read-only optimizations.
- DBT-2/TPC-C-like: ~5% slowdown vs SI with "safe snapshot" read-only optimizations.
- RUBiS: SSI 422 req/s vs SI 435 req/s (~3% cost) vs strict 2PL 208 req/s — SSI ~2× S2PL on read-heavy ([numbers](https://mliudb.wordpress.com/2020/04/20/serializable-snapshot-isolation-in-postgresql/)).
- Engineering: separate predicate lock manager, bounded memory via SLRU summarization of old transactions' locks, *deferrable read-only transactions* waiting for a "safe snapshot" then running with zero SSI overhead.

**When SI suffices — crucial for sparq's design.** Write skew requires *two concurrent read-write transactions*. If writers are serialized (single-writer: one bulk SPARQL UPDATE at a time, applied against latest committed state), the pivot structure cannot form among writers, and read-only transactions can never be pivots (a pivot needs an *outgoing* rw-antidependency, i.e. a write). Therefore **a single-writer store with snapshot reads is trivially serializable: SI = serializability, and the entire SSI apparatus is dead weight**. Only residual requirement: each UPDATE's read (WHERE evaluation) and write happen against the same generation it replaces — serialized writers guarantee this.

## A.2 Deterministic / batched transaction reordering

- **Calvin (Thomson et al., SIGMOD 2012)** ([paper](https://cs.yale.edu/homes/thomson/publications/calvin-sigmod12.pdf)): sequencers collect transactions into **10 ms epochs**, agree on global deterministic order, then schedulers lock in that order — no 2PC, near-linear scaling to **~500k TPC-C NewOrder tps on 100 nodes**. Hard prerequisite: read/write sets known (or "reconnaissance queries") before ordering.
- **Bohm (Faleiro & Abadi, VLDB 2014/15)** ([PVLDB 8(11):1190](http://www.vldb.org/pvldb/vol8/p1190-faleiro.pdf)): deterministic MVCC — batch serialization order fixed up front; partitioned version-placement phase pre-creates version metadata so **reads do zero bookkeeping** (no contended shared-memory writes on the read path — directly relevant to read-mostly stores). CC layer alone ~2M txn/s; on high-contention YCSB **>2× Hekaton/SI/OCC/locking**. Same prerequisite: pre-declared write sets.
- **Doppel (Narula et al., OSDI 2014)** ([paper](https://pdos.csail.mit.edu/papers/doppel:osdi14.pdf)): commutative updates (increments, max, set-insert) to contended records go to per-core copies in a split phase, merged later.
- **H-Store / Strife.** H-Store (VLDB 2007/2008): each partition single-threaded, **no CC at all** — serial execution as the fast path when workloads partition. Strife ([SIGMOD 2020](https://homes.cs.washington.edu/~suciu/guna-sigmod-2020-pdfa.pdf)): per-batch clustering (bipartite txn–data graph) into conflict-free clusters executed in parallel without CC + residual cluster; up to **2× over 2PL** under contention.

**Honest verdict for a single-writer RDF store with bulk SPARQL UPDATE:** this literature mostly does NOT apply — its problem (extracting parallelism from contended multi-writer OLTP of small transactions) is dissolved by single-writer design. (1) Calvin/Bohm pre-declared write sets are a poor fit for `DELETE/INSERT ... WHERE` (read/write sets query-determined and unbounded; reconnaissance execution = a slower single writer). (2) Strife/H-Store clustering presupposes many concurrent small transactions; one bulk UPDATE is one cluster. What DOES transfer: (a) **epoch/group commit** — amortizes generation publication for a COW store (one new generation per epoch, not per statement); (b) **Bohm's read-path discipline** — readers do zero shared-memory writes (no refcount bumps on hot lines if avoidable, no read tracking); (c) **commutativity** — `INSERT DATA`/`DELETE DATA` commute when triple sets are disjoint (set semantics), so queued pure-data updates can merge into one batch regardless of arrival order, while any `DELETE/INSERT WHERE` is a reorder barrier. Realistic, modest payoff: batch and merge commuting updates between barriers; don't build a deterministic scheduler.

## A.3 Snapshot retention costs in real systems

- **PostgreSQL:** long-running transactions hold back the **xmin horizon**; VACUUM reports rows "dead but not yet removable"; bloat accumulates until the oldest snapshot releases ([pganalyze](https://pganalyze.com/docs/checks/vacuum/xmin_horizon); [Citus](https://www.citusdata.com/blog/2022/07/28/debugging-postgres-autovacuum-problems-13-tips/); [CYBERTEC](https://www.cybertec-postgresql.com/en/reasons-why-vacuum-wont-remove-dead-rows/)). Retention cost is *global* (whole-table bloat), not proportional to what the reader touches.
- **RocksDB:** snapshots/iterators pin a Version of the LSM tree; **all SSTs in that version excluded from deletion even after compaction**; iterators also pin flushed memtables ([Delete Stale Files](https://github.com/facebook/rocksdb/wiki/Delete-Stale-Files); [Iterator](https://github.com/facebook/rocksdb/wiki/Iterator)). Long snapshots also prevent dropping overwritten values/tombstones → space amp grows with write volume during the snapshot's lifetime.
- **LMDB:** COW B-tree; readers pin the page version at their txnid; pages freed by later writers can't be recycled until the oldest reader finishes — docs warn the DB "may grow rapidly, devolving into append-only behavior" under long readers ([lmdb.tech](http://www.lmdb.tech/doc/); [How LMDB works](https://xgwang.me/posts/how-lmdb-works/)). Freelist pathology: Erigon's ~900k-entry freelists spilling into overflow pages, slowing every write txn ([Erigon notes](https://github.com/erigontech/erigon/wiki/LMDB-freelist-illustrated-guide)). Canonical cautionary tale for "readers pin generations."
- **Oxigraph:** RocksDB-based; "reads isolation is implemented by taking a snapshot of the database state at the beginning of the read operation" (repeatable-read per query/update); moved TransactionDB → WriteBatchWithIndex, deliberately trading some ww-conflict detection for faster updates ([Architecture wiki](https://github.com/oxigraph/oxigraph/wiki/Architecture); [Store docs](https://docs.rs/oxigraph/latest/oxigraph/store/struct.Store.html)). De-facto RDF standard = "snapshot per query," inheriting RocksDB pinning economics.
- **COW / persistent-structure alternative.** *Left-right* (Ramalhete & Correia): two full instances; wait-free reads, writes apply twice, writer blocks until readers drain — **permanent 2× memory**, blocked writers, zero GC machinery ([HAL](https://hal.science/hal-01207881); [Concurrency Freaks](http://concurrencyfreaks.blogspot.com/2013/12/left-right-concurrency-control.html)). The **Arc-swapped immutable generation** pattern ([arc-swap docs](https://docs.rs/arc-swap/latest/arc_swap/): "read-mostly, update-seldom"; lock-free wait-free `load`) + persistent structures (HAMT/B-tree structural sharing) is strictly better-behaved than LMDB/RocksDB retention: a new generation copies only O(Δ·log n) nodes on modified paths; an old generation held by a straggler retains only the *delta nodes* vs current (shared nodes cost nothing); reclamation automatic when the last Arc drops — no vacuum, no freelist. Honest caveats: (1) a wedged reader still pins memory unboundedly as deltas accumulate → generation-age metrics + query timeouts needed; (2) refcounted persistent nodes make readers bump refcounts unless per-generation arenas or epoch-based reclamation are used — Bohm's zero-bookkeeping-read lesson; (3) path-copying write amplification makes per-statement generations expensive — exactly why epoch/batched commit (§A.2) pairs with this design.

# Topic B — RDF/SPARQL benchmarks for concurrent serving

## B.1 BSBM (Berlin SPARQL Benchmark)

E-commerce dataset. **Explore** mix = 25 queries from 12 SPARQL 1.0 templates per mix; **Explore-and-Update** adds SPARQL 1.1 Update (INSERT offers/reviews, DELETE). Primary metric **QMpH**; secondary per-query QpS, AQET, load time ([spec V3.1](http://wbsg.informatik.uni-mannheim.de/bizer/berlinsparqlbenchmark/spec/index.html); [rules](http://wbsg.informatik.uni-mannheim.de/bizer/berlinsparqlbenchmark/spec/BenchmarkRules/index.html)). **Concurrency model: closed-loop.** N client threads (official runs: **1, 4, 8, 64 clients**), each running mixes back-to-back with distinct seeds; warm-up then measured mixes (V7: ≥8,000 ramp-up, 500 measured) ([V7 2013](http://wbsg.informatik.uni-mannheim.de/bizer/berlinsparqlbenchmark/results/V7/index.html); [V6 2011](http://wbsg.informatik.uni-mannheim.de/bizer/berlinsparqlbenchmark/results/V6/index.html)). Measures aggregate closed-loop throughput; does NOT measure latency at fixed arrival rate — a slow query throttles its own client → under-reports tail pain (coordinated omission).

## B.2 LDBC SNB Interactive (v1 SIGMOD 2015; v2 2023)

([Erling et al. SIGMOD 2015](https://dl.acm.org/doi/10.1145/2723372.2742786); [v2, arXiv 2307.04820](https://arxiv.org/pdf/2307.04820)). Driver **replays a simulated timeline**: every operation has a *scheduled start time*; **Time Compression Ratio** scales to wall clock. Score = throughput at the lowest sustainable TCR subject to **95% of operations starting within 1 s of schedule**. 30-min warm-up + 2-h measurement; per-op min/mean/max/P50/P90/P95/P99. v2 mix: **~8% complex reads, ~72% short reads, ~20% inserts, ~0.2% deletes**; dependency-tracked updates (T_safe = 10 s); v2's 8 cascading **deletes** push required isolation up to **snapshot isolation**; scales to SF30,000 (82.76B nodes, 340.5B edges). Scheduled arrivals + on-time rule = the standard countermeasure to *coordinated omission* (Gil Tene): stalls show up as on-time violations and fat P99s instead of vanishing.

## B.3 WatDiv

([Aluç, Hartig, Özsu, Daudjee](https://dsg.uwaterloo.ca/watdiv/)). Data generator + query-template generator; basic suite **20 templates in 4 classes — Linear, Star, Snowflake, Complex** — wide selectivity/shape ranges, deliberately heterogeneous entity schemas. Measures plan-space/optimizer coverage and raw latency, single-stream. **No native concurrency, no updates, no arrival model** — raw material (query pool with controlled diversity) for an external load driver.

## B.4 IGUANA and endpoint-under-load studies

**IGUANA** ([Conrads et al., ISWC 2017](https://link.springer.com/chapter/10.1007/978-3-319-68204-4_5); [GitHub](https://github.com/dice-group/IGUANA)): benchmark-agnostic execution framework — any query set + optional changesets, configurable **stresstest** with pools of query workers and update workers in parallel. **Closed-loop** (each worker issues the next query when the previous returns/times out; current rewrite: `SPARQLProtocolWorker` with `number`, `completionTarget`, per-query `timeout` ([worker docs](https://dice-group.github.io/IGUANA/docs/latest/configuration/workers/))). Metrics: QPS per query, **QMPH**, **NoQ/NoQPH**, AvgQPS, **penalized QPS** (failed/timed-out queries charged a fixed penalty so engines can't score by failing fast). Inherits coordinated omission.

**Public endpoints under load:** [Buil-Aranda et al., ISWC 2013](https://aidanhogan.com/docs/epmonitorISWC.pdf): **427 public SPARQL endpoints**; generic-query performance varied **3–4 orders of magnitude**; only **32.2%** high availability over 27 months. Motivation: real SPARQL serving is availability/tail-latency constrained.

## B.5 Honest adaptation for sparq

BSBM = realistic read/update *mix* + QMpH convention (closed-loop); WatDiv = *query-shape coverage*, no concurrency; SNB Interactive = the only defensible *arrival model* (scheduled starts, 95%-on-time, dependency-tracked updates, SI required once deletes exist); IGUANA = reusable multi-client *harness* with failure-penalized metrics, closed-loop. An honest concurrent-serving evaluation for a single-writer/COW RDF store should: (1) take query pools from BSBM Explore(-and-Update) + WatDiv; (2) drive them **open-loop at fixed arrival rates** (LDBC-style schedule, or IGUANA + external rate controller), recording HdrHistogram-style P50–P99.9 and reporting *throughput at an SLO* ("max ops/s with P99 < X ms and ≥95% on-time"), not bare QMpH; (3) include a sustained update stream concurrent with reads, stating the delivered isolation level (SNB v2 deletes force ≥SI — generational single-writer provides it natively); (4) add the test no standard suite includes but §A.3 shows is the real failure mode: a deliberately long-running analytical query held open during heavy updates, tracking memory growth (generation retention) and update-latency degradation — measure the LMDB-style pinning pathology directly rather than letting closed-loop throughput hide it.
