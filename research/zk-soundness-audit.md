# ZK prover/verifier soundness audit

Adversarial soundness audit of the merged sparq ZK proof system (crates/sparq-zk, crates/sparq-zk-compose, zk/compose), run 2026-06-13 as a multi-agent workflow: threat map + 7 attack lenses + 2 independent verifiers per finding + synthesis (59 agents).

## Assurance statement

v1 verifier soundness is BROKEN. verify_manifest provides NO meaningful soundness guarantee to a relying party: a prover can forge arbitrary query results that the verifier accepts with Ok(()). The two load-bearing cryptographic gates are both absent in code — the bb-verified public_inputs are never reconstructed from / compared against the declared manifest statement, and the verification key handed to `bb verify` is taken verbatim from the prover's own proof_hex blob rather than recomputed from the canonical compiled circuit. Either gap alone lets a prover attach a genuine (or trivially-circuit) bb proof while the manifest JSON advertises a different, false result. On top of that, the credential trust model is entirely unimplemented (no issuer signature, no key-set membership, unsigned prover-chosen commitments), there is zero replay/freshness binding (every manifest is infinitely replayable), the query text / FILTER operator-bound-verdict / operand-slot are never bound to the proof, and revocation is unchecked. The one robust gate (the verify.rs fragment + cross-graph bnode-join recheck) is sound in isolation but worthless on top of an unbound pipeline, and is itself bypassable via prover-declared attributions. DO NOT present v1 as proving anything to a relying party. It is a faithful research scaffold of the in-circuit relations (scan completeness/soundness and filter comparison ARE correct in-circuit), but the verifier-side binding layer that would make those relations mean anything to a third party does not exist yet.

## Confirmed issues (12)

### 1. [CRITICAL] bb-verified public_inputs are never reconstructed from or compared to the declared manifest statement (forge arbitrary results)
**Location:** crates/sparq-zk-compose/src/verifier.rs verify_manifest (lines 199-219) and decode_artifacts (234-242); missing reconstruction belongs at ~line 211 using manifest.binding + sp.inputs in main declaration order

Stages 1-2 (recheck, derive_id, binding edges) inspect only the declared ProofInputs JSON. Stage 3 decodes (proof, public_inputs, vk) straight from the prover-controlled sp.proof_hex blob and passes public_inputs verbatim to `bb verify -i`. The verifier never serializes the public-input field vector from the declared commitments/pattern_*/rows/row_count/operand_enc/op/bound/expected (+ its own challenge) and asserts byte-equality with art.public_inputs. So Stages 1-2 check a JSON statement, Stage 3 checks a detached cryptographic proof over a DIFFERENT (prover-chosen) public-input vector, and nothing checks the two describe the same statement. An adversary generates an honest bb proof over any small true statement it legitimately holds (no malicious circuit needed), then writes a false ProofInputs::Scan (different commitments, fabricated rows, altered row_count) into the manifest while leaving proof_hex pointing at the honest proof; derive_id still passes if k/r buckets match (trivially tuned). Both exploit-builder verdicts confirmed_exploitable; no guard exists (whole-crate grep shows art.public_inputs flows only into decode/encode and driver.verify's bb -i, never a comparison).

**Fix:** Before/independent of bb verify, reconstruct the public-input field vector from the declared ProofInputs (in `main` declaration order: challenge, commitments, pattern_is_const, pattern_const_enc, rows, row_count for scan; challenge, operand_enc, op, bound, expected for filter) using the verifier's OWN fresh challenge, serialize to the exact bb public_inputs byte format, and assert byte-equality with art.public_inputs. Reject on any mismatch. This is the single most load-bearing missing check; nothing else in the verifier means anything until it exists.

### 2. [CRITICAL] bb verify uses the prover-supplied verification key, never the canonical circuit vk
**Location:** crates/sparq-zk-compose/src/verifier.rs verify_manifest (199-219) + decode_artifacts (234-242); crates/sparq-zk-compose/src/driver.rs verify (181-203) writes art.vk and passes it to `bb verify -k`

decode_artifacts splits the prover blob into (proof, public_inputs, vk) and CircuitProver::verify (driver.rs:181-203) writes art.vk verbatim and runs `bb verify ... -k <prover_vk>`. The verifier never recomputes the vk from the compiled circuit member named by the re-derived CircuitId, never loads a pinned/content-addressed vk, and never compares vk bytes to a trusted store. The verify() function takes no CircuitId at all. The inline comment at verifier.rs:204-209 falsely claims 'we recompute the vk from the compiled member' — no such recomputation exists (the only compile/--write_vk calls are in driver.rs prove(), the prover path). An adversary compiles a trivial Noir circuit with the same public-input arity as a real scan member but zero soundness constraints, bb prove --write_vk over fabricated public inputs, bundles (proof, public_inputs, attacker_vk), and bb verify accepts because the triple is internally consistent for the attacker's own vk. derive_id passes (k/r match, n trusted). Both exploit-builder verdicts confirmed_exploitable; no guard found.

**Fix:** Recompute the vk on the verifier side from the canonical compiled circuit member named by the re-derived CircuitId (nargo compile + bb write_vk), or load it from a trusted content-addressed store keyed by CircuitId, and use THAT vk for bb verify — never the prover-supplied vk. Combined with the public-input reconstruction above, this closes the cryptographic gate.

### 3. [CRITICAL] No issuer-signature / key-set membership check anywhere: commitments are unsigned prover-chosen field elements (arbitrary graph forgery and triple suppression)
**Location:** crates/sparq-zk/src/commit.rs commit_triples/commit_canonical (no signature); crates/sparq-zk-compose/src/verifier.rs verify_manifest (192-221, no registry/signature cross-check); crates/sparq-zk/src/registry.rs (issuerKey recorded as IRI only); zk/compose/compose_core/src/scan.nr step 1 (commitment is a prover-supplied public input)

C(G) is computed entirely prover-side via poseidon2::hash over leaves the prover supplies, under any salt, with no signature. The scan circuit only proves commit_fold(witnessed_leaves, count) == commitments[g] for a prover-supplied commitments[g]. verify_manifest never reads the registry, never verifies a signature, never resolves issuer keys, never compares commitments[] to any attested value; manifest.rs documents 'issuers' as informational and 'signature check deferred' in v1. Spec clause S(a) (each commitment signed by a key in disclosed set K) is wholly unimplemented. Consequently a prover commits to ANY triple set it invents, or to a strict subset of a genuine credential (drop the suspension/revocation triple, recompute C over the truncated leaf list, prove) — the headline suppression the spec claims to prevent is fully available. This works with the HONEST scan circuit, honest vk, honest public inputs, so it is independent of the two binding gaps above. The verifiers split (exploit-builder rated confirmed_weakness_not_exploitable because it is a missing feature rather than a fooled check; guard-finder rated confirmed_exploitable). Consolidated as a CONFIRMED CRITICAL gap against the intended guarantee: the documented headline use case ('a credential issued by X') has zero cryptographic backing — the prover is effectively the issuer of every fact it proves.

**Fix:** Bind every commitment to an issuer signature: verify Sign(pk_i, C(G_i)) with pk_i in the disclosed key-set K, either in-circuit (preferred for full ZK) or, at minimum, verifier-side by resolving issuer keys and checking a signature over each commitments[g] before accepting the manifest. commitments[] must never be an unsigned prover-chosen public input. Until this lands, document loudly that v1 proves nothing about credential provenance.

### 4. [CRITICAL] No replay/freshness binding: every manifest is infinitely replayable across queries, sessions, holders and relying parties
**Location:** crates/sparq-zk-compose/src/verifier.rs verify_manifest (192-221, no nonce param, never reads manifest.binding/challenge); zk/compose/*/src/main.nr `let _ = challenge` (unconstrained tag, by design); crates/sparq-zk/src/manifest.rs BindingMode (82-100)

verify_manifest takes no verifier-issued nonce, never compares the proof's challenge to a fresh value, and never tracks single-use. The challenge is the first public input of every circuit but is unconstrained in-circuit (a tag, correct design IF the verifier bound it). manifest.binding.challenge() is a prover-written JSON field that has ZERO call sites in the verifier (the only `.binding`-prefixed read is the unrelated binding_edges loop). Every stage is a deterministic function of the manifest bytes, so a captured manifest verifies forever, against any relying party, in any session. Additionally (challenge-rebind finding), even a hardened deployment that adds the obvious patch `manifest.binding.challenge() == N` is defeated by a single JSON string substitution, because that JSON field is decoupled from the challenge committed inside the bb public_inputs (which the verifier never inspects). All four replay/rebind exploit-builder verdicts confirmed_exploitable; no guard found. Severity raised to critical for a credential system (replayable bearer proofs).

**Fix:** verify_manifest must (i) accept a verifier-issued fresh nonce as a parameter, (ii) inject it as the challenge when reconstructing the public-input vector (see the public-input-binding fix) and assert it equals the challenge bytes inside art.public_inputs, and (iii) enforce single-use (a seen-nonce store). The JSON BindingMode.challenge is only meaningful once it is byte-bound to the proof via the reconstruction.

### 5. [CRITICAL] FILTER operator / bound / verdict are never bound to the query's FILTER expression — prover substitutes the comparison
**Location:** crates/sparq-zk-compose/src/verifier.rs derive_id (113-123, `let _ = bound;`); crates/sparq-zk/src/verify.rs recheck + expression_has_exists (159-184, FILTER operator/operand never extracted)

The verifier re-parses the query only to extract BGP patterns and reject EXISTS. The FILTER comparison nodes (Greater/GreaterOrEqual/Less/Equal) are walked solely inside expression_has_exists to look for EXISTS, discarding the operator and the literal operand; the projection list is discarded via `..`. derive_id explicitly throws away the filter bound (`let _ = bound;`) and never reads op or expected. So nothing ties a FilterInt sub-proof's declared (op, bound, expected) to the FILTER the relying party reads in manifest.query. A credential with age=17 against FILTER(?age >= 18) (honest verdict false, drop the row) is proven by a filter_int sub-proof over op=Ge, bound=17, expected=true (17>=17 genuinely true — a satisfiable instance of the same circuit family d=2). The binding edge equality holds (operand really is Enc(17)), bb verifies the true (17>=17) instance, recheck ignores the comparison. The relying party reads >=18 and a non-empty result and concludes age>=18 — false. Independent of the public-input/vk gaps (each sub-proof is honest). Both exploit-builder verdicts confirmed_exploitable; no guard found.

**Fix:** Parse the query's FILTER expression into (variable, operator, constant) and require a matching FilterInt sub-proof whose declared op/bound equal the query's operator/constant, whose operand variable is the FILTER's variable (mapped to a concrete scanned slot), and whose expected verdict gates row inclusion (expected==false rows must be excluded, expected==true required). Fold op/bound/expected into the reconstructed public-input vector so the binding is cryptographic, not JSON-only.

### 6. [HIGH] Binding edge does not check the operand slot is the FILTER's operand variable, nor that the verdict prunes the row
**Location:** crates/sparq-zk-compose/src/verifier.rs verify_manifest_structure stage 2 (161-185); crates/sparq-zk/src/verify.rs (no FILTER-variable-to-slot mapping)

Stage 2 only asserts scan.rows[from_row][from_slot] == filter.operand_enc as a FieldHex equality over declared JSON. Nothing checks that from_slot is the column the FILTER actually constrains (the FILTER's operand variable), nor that a row with expected==false is excluded from the disclosed result. The prover chooses which scanned slot to call 'the operand'. For a pensioner query SELECT ?p WHERE { ?p <hasSalary> ?sal . ?p <hasAge> ?age . FILTER(?age >= 65) }, the prover points from_slot at the SALARY object encoding of a row whose salary 70000 satisfies (op=Ge, bound=65); operand_enc equals the salary slot, the equality passes, bb verifies 70000>=65==true. The disclosed rows (with real, failing ages) are presented as passing the age filter. Independent of the public-input/vk gaps (sub-proofs are honest). Both exploit-builder verdicts confirmed_exploitable; no guard found.

**Fix:** Derive, from the query FILTER, the exact (pattern, slot) the operand variable binds to, and require the binding edge's (from_proof, from_row, from_slot) to be that slot of the scan proof for that pattern; and gate row inclusion on the verdict (expected). This depends on the FILTER-binding fix above (mapping the FILTER variable to a slot).

### 7. [HIGH] Binding edges and circuit-id re-derivation operate over declared JSON only; operand substitution / kind confusion is undetectable
**Location:** crates/sparq-zk-compose/src/verifier.rs stage 2 (161-185) and stage 1b derive_id (95-125); no reconstruction of bb public_inputs

The composition seam 'scanned column equals filter operand' is a FieldHex string equality over two prover-written JSON fields, and the kind dispatch (Scan source / FilterInt target) is a Rust enum-tag check on the JSON, not a property of the attached proofs. Because public_inputs are never bound to the JSON (see the catastrophic public-input gap), a prover declares rows[r][slot]=O and operand_enc=O in JSON (stage 2 passes), attaches a genuine filter_int bb proof generated over a DIFFERENT operand O' (e.g. value 99 satisfying >=18) with its own bundled vk/public_inputs (stage 3 passes for that detached proof), and the two cryptographic pieces are never linked. The scanned column and the filtered column are never cryptographically equated. Both exploit-builder verdicts confirmed_exploitable; no guard found. This is the public-input-binding gap specialized to the scan->filter seam.

**Fix:** Fold operand_enc into the reconstructed-and-byte-compared public-input vectors of BOTH the scan proof (the disclosed row slot) and the filter proof (operand_enc), so the binding edge equality is enforced over bb-bound values, not declared JSON. This is subsumed by fixing the public-input binding gap plus the operand-slot fix.

### 8. [CRITICAL] Verifier bnode cross-graph join guard is driven by prover-declared attributions, which are unbound to the proof
**Location:** crates/sparq-zk/src/verify.rs cross_graph_join_obligations (248, cross_possible test) + recheck (269-282); crates/sparq-zk-compose/src/verifier.rs verify_manifest_structure (133-146, attributions taken verbatim); zk/compose/compose_core/src/scan.nr (no per-row graph attribution in-circuit)

The Q6 join-obligation gate decides whether a cross-graph join needs a non-bnode obligation purely from manifest.attributions, a prover-controlled JSON field never cross-checked against any proof-bound quantity. The scan circuit deliberately does not bind per-row graph attribution (a disclosed row need only occur in SOME active slot of SOME committed graph; scan.nr:26-29, 80-91), so an honest bb proof cannot refute a false attribution. A prover whose witnessed data joins a bnode-valued variable across two genuinely distinct graphs declares both joined patterns as drawn from the SAME single graph (attributions=[[0],[0]]); cross_graph_join_obligations computes |{0}|=1, cross_possible=false, no obligation is required, recheck returns Ok([]). The cross-graph bnode correlation that Q6 exists to forbid is admitted, leaking that two undisclosed credential graphs share an entity — contradicting the module-doc claim (verify.rs:20-23) that a malicious prover cannot smuggle a correlating join past an honest verifier. The honest prover-side bnode_guard (trace.rs) is adversary-controlled and never re-run verifier-side. Both exploit-builder and guard-finder verdicts confirmed_exploitable; no guard found. Independent of the public-input gap (attributions are not public inputs).

**Fix:** Bind per-row source-graph attribution in-circuit: add an attribution witness to scan_check that constrains each disclosed row to occur in a slot of a DECLARED graph index, surface the per-pattern attribution as a public input, and reconstruct+compare it against manifest.attributions in the verifier. Then the recheck obligation logic operates over a proof-bound attribution map. (Hardening alternative below also enforces salt uniqueness, but in-circuit attribution is the load-bearing fix.)

### 9. [HIGH] Cross-graph bnode salt-separation has no verifier or in-circuit enforcement; a salt-reusing ingester can correlate bnodes across graphs
**Location:** crates/sparq-zk/src/encode.rs encode_term (56-59, salt mixed only off-circuit); crates/sparq-zk-compose/src/build.rs build_scan (~110, salt off-circuit); zk/compose/compose_core/src/scan.nr (salt never in-circuit); crates/sparq-zk/src/registry.rs (no salt-uniqueness check)

The entire Q6 'bnodes from different graphs are distinct by construction' guarantee rests on each graph being committed under a distinct per-graph salt. But the salt is a pure prover input: encode_term mixes it off-circuit, scan.nr recomputes commitments directly from already-encoded enc[g][i] (the salt never enters any circuit), and the verifier never sees or compares salts (grep: salt absent from verifier.rs and every .nr relation). registry.rs/commit.rs accept any caller-supplied salt with no uniqueness check, and there is no production OS-random salt ingest path (salt_from_bytes is test-only). An adversary-ingester commits two graphs under the same salt S; a bnode with the same canonical label then encodes to the identical field element in both commitments, turning it into a cross-graph correlation handle behaving like a shared IRI. The verifiers split (exploit-builder confirmed_weakness_not_exploitable on the narrow ground that the verifier observes only opaque field elements and the adversary must own both graphs; guard-finder confirmed_exploitable as a privacy/correlation break). Consolidated as a CONFIRMED HIGH privacy/merge-distinctness gap: the in-circuit and verifier enforcement the Q6 design assumes does not exist, and the random-salt ingest is unimplemented.

**Fix:** Either (a) enforce globally-unique per-graph salts at a trusted ingest (draw 32 OS-random bytes per graph at registry mint, and have the verifier/issuer-signature bind the salt so reuse is detectable), or (b) bind the salt into the in-circuit attribution check so cross-graph bnode equality is provably impossible without distinct salts. The privacy property must not rest on an unenforced, unimplemented honest-ingest convention.

### 10. [HIGH] Query text is not bound into the proof: a proof for query Q1 can be presented under a different query Q2 (FILTER-add / constant-swap replay)
**Location:** crates/sparq-zk-compose/src/verifier.rs verify_manifest_structure stage 1a (132-146); crates/sparq-zk/src/verify.rs collect_patterns (121-156, projection and FILTER expr discarded)

The SPARQL query lives only in manifest.query and is checked solely by recheck (fragment/bnode/arity), which validates the query against declared attributions but does NOT bind it to any proof. The scan public inputs commit only to per-pattern constants/rows/commitments/row_count — no query digest, no projection, no FILTER set. collect_patterns discards the projection list (`Project { .. }`) and the FILTER expression (Filter checked only for EXISTS, then recurses into inner). An honest scan-only manifest for { ?s <ex/age> ?o } is accepted under Q2 = SELECT ?s ?o WHERE { ?s <ex/age> ?o FILTER(?o >= 100) }: recheck sees one BGP pattern, passes; stages 1b/2/3 are query-independent; the relying party reading manifest.query believes the disclosed (complete, UNFILTERED) rows all satisfy >=100. A constant swap (age scan presented as a salary answer) works identically since pattern_const_enc is never compared to the query-derived constants. Both exploit-builder verdicts confirmed_exploitable; no guard found. (Projection-narrowing and FILTER-drop directions stay true and are not breaks; FILTER-add/change and constant-swap are the genuine forgeries.)

**Fix:** Bind the query to the proof: fold a canonical digest of the full normalized query (projection, BGP constants, FILTER operators+constants) into the reconstructed public-input vector and byte-compare; and cross-check each query BGP pattern's constant slots against the scan proof's pattern_const_enc, and each query FILTER against a required FilterInt sub-proof (see the FILTER-binding fix).

### 11. [HIGH] Circuit-id re-derivation trusts declared n (and d): size-bucket downgrade/relabel undetectable
**Location:** crates/sparq-zk-compose/src/verifier.rs derive_id (95-125); crates/sparq-zk-compose/src/build.rs derive_scan_id (31-38) / derive_filter_int_id (41-44)

derive_id re-derives only k (commitments.len) and the r bucket (rows.len max row_count); it reads declared_n straight out of the declared id and feeds it to derive_scan_id, where smallest_bucket([16,64], declared_n) round-trips any compiled bucket unchanged, so derived.n == declared.n tautologically. The same holds for FilterInt's d. The r-bucket is also derived from the disclosed active-row count, not the producing circuit's bucket, so an honest r=8 proof disclosing 4 rows relabels cleanly to r=4. The plan S2.4 'verifier re-derives the circuit id from the public statement' rule is therefore unmet on the n/d/r-relabel axes. The verifiers split: against the catastrophic public-input/vk gaps this lets the attacker freely choose the advertised bucket (a force-multiplier, confirmed by the n-downgrade and kind-confusion exploit-builders); standalone, the n/d relabel is bucket-invariant on the commitment scheme (commit_fold IV is count, not N) and so attests the same statement (guard-finder confirmed_weakness_not_exploitable). Consolidated as a CONFIRMED HIGH soundness-rule deviation that is subsumed by, and only fully fixed alongside, the vk/public-input binding fixes.

**Fix:** Pin the vk per family member keyed by the FULL re-derived CircuitId (k,n,r / d) and select the verification vk by that id (the vk-authenticity fix). Once the vk is the canonical member's and the public-input vector is reconstructed and byte-compared, a declared n/d/r inconsistent with the actual proof fails. n itself cannot be re-derived from public data (graph size is private), so binding it via vk selection + public-input layout is the only sound route.

### 12. [MEDIUM] Revocation entirely unimplemented and status-list index disclosed in the clear
**Location:** crates/sparq-zk-compose/src/manifest.rs RevocationStatus (index in clear); crates/sparq-zk-compose/src/verifier.rs (ignores `revocation`)

RevocationStatus records a status-list index as a clear field; the verifier never checks revocation/non-revocation, there is no in-circuit status-list inclusion + bit-unset proof, and no freshness-window/now check. A suspended or revoked credential still verifies. The clear index is also a linkability channel contradicting the privacy claims. Per the threat map (invariant S2.6, weakest-link #6) this is unimplemented; no verifier reads `revocation`. Confirmed as a real medium gap against the intended guarantee (no exploit dispute needed — the feature is simply absent).

**Fix:** Implement S2.6: a hidden-index status-list inclusion proof + bit-unset assertion in-circuit, bound to a disclosed status-list version, plus a verifier freshness-window check; do not disclose the index in the clear.

## Hardening recommendations (7)

- Funnel ALL blob-decode failures through the CheckError REJECT channel: hex_decode (verifier.rs:263-268) panics via .expect("valid hex") and an OOB slice on non-hex/odd-length input; take_lp (249-253) panics on a <4-byte buffer or an oversized length prefix. These are prover-controlled and reach the verifier before any bb call, so a single malformed proof_hex field crashes/aborts an in-process verifier (release profile sets panic="abort"). It is a DoS, not a false-accept, but make hex_decode/take_lp return Result and add a CheckError::MalformedProof variant so every stage-3 failure path rejects rather than panics (mirroring the existing empty-proof_hex MissingProof guard).
- Constrain row_count to a definite cardinality in-circuit (or document loudly that it is a distinct RDF-merge set-count, never an occurrence/multiset count). Today scan.nr asserts only row_count <= R, and the set-membership OR-accumulators let a single disclosed row discharge completeness for identical matching slots across multiple graphs, and let a prover both under- and over-report. The verifier uses row_count only to size the r bucket. Harmless under documented union semantics, but a relying party that reads row_count as 'number of credentials' is misled.
- Normalize literal lexical forms (or reject non-canonical/signed xsd:integer) before encoding: filter_int.nr can only bind a canonical non-negative decimal token, so a committed "007"/"-5" literal is unbindable by any filter proof. Combined with the missing FILTER-coverage gate this lets a prover keep/drop FILTER-constrained rows by lexical-representation choice. Add lexical normalization in canon.rs/encode.rs and/or require a bound filter proof per FILTER-constrained row.
- Make commit_fold length-binding explicit: counts[g] is an unconstrained private witness baked into the Poseidon2 length IV, and the Rust commit uses leaves.len(); they agree only when the prover is honest. Collision-resistant in isolation (the length IV gives domain separation), but once issuer signatures bind a commitment, also bind the true triple count into the signed object so a short-count view cannot be presented.
- Add per-config end-to-end negative tests that exercise the verifier's binding gates once they exist: a manifest whose proof_hex is an honest proof over a DIFFERENT statement than the declared ProofInputs must be REJECTED; a manifest with a prover-supplied non-canonical vk must be REJECTED; a replayed manifest under a fresh nonce must be REJECTED; an attributions=[[0],[0]] cross-graph bnode join must be REJECTED. The current e2e suite only covers happy-path + an r-tamper circuit-id-mismatch and an honestly-declared [[0],[1]] cross-graph rejection.
- Remove or correct the misleading inline comments that claim guarantees the code does not deliver (verifier.rs:204-209 'we recompute the vk from the compiled member'; scan.nr replay-binding-by-verifier note; verify.rs:20-23 'a malicious prover cannot smuggle a correlating join past an honest verifier'). False assurance comments are a hazard in a security-critical module under active review.
- Treat HolderPop as the documented placeholder it is: it carries a `holder` IRI but performs zero proof-of-possession (no signature, no key, no DPoP challenge-signed-by-holder-key), and verify_manifest never reads it. The schema is live and serializable; either gate its use behind an explicit 'unimplemented' error or implement holder-key PoP before any relying party trusts sender-constraint.

## Attacks considered & refuted/guarded (7)

- Cross-graph bnode join via salt collision smuggled past the join-obligation gate (salt-unbound-forge-2): the salt collision itself is invisible to the gate, but the gate (verify.rs cross_graph_join_obligations, 248) is value-blind and salt-INDEPENDENT — it flags any join edge with |A_i ∪ A_j| > 1 lacking a declared non-bnode obligation. So a salt collision cannot evade it; the only way past is an attribution LIE, which is the separate bnode-attr-forge-1 issue (confirmed above), not a salt issue. Also: the same harm (joining facts about one bnode entity) is legitimately achievable in a single graph (attributions [[0],[0]], no obligation required — verify.rs:248,338-345). Guard cited: verify.rs recheck/cross_graph_join_obligations (231-282). The standalone salt-collision break is therefore subsumed, though the unbound-salt PRIVACY gap is confirmed separately above.
- Vacuous non-bnode obligation (bnode-vacuous-obligation-2): the demanded obligation is satisfied by a bare JSON line in join_obligations with no type check, which is a real nominal-obligation weakness. But in the finding's own scenario (honest plural attributions [[0],[1]] with honest distinct per-graph salts), the disclosed bnode encodings are UNEQUAL by construction (encode.rs:56-58 salt-separation), so the downstream join produces no correlated row. Guard cited: encode.rs:56-58 salt-separated bnode encoding (verified by commit.rs salt_separation test). Turning it into a real correlation requires salt reuse (the confirmed bnode-salt-collide gap above) or an attribution lie (confirmed bnode-attr-forge above); the vacuous-obligation gap alone is not an independent break.
- row_count set-vs-multiset deduplication (scan-rowcount-set-not-multiset-1): mechanically real (set-membership OR-accumulators dedup identical ground triples across graphs), but under the system's DECLARED RDF-merge/union semantics the deduplicated set-count is the CORRECT answer, and no verifier code or spec interprets row_count as an occurrence count (verifier.rs:110 `let _ = row_count`, used only to size the r bucket). Guard cited (semantic): scan.nr:14-17 'complete w.r.t. the union' + encode.rs:14 'exactly RDF merge semantics'. Not a soundness break; listed as hardening (document row_count's meaning).
- commit_fold count unconstrained (commit-fold-count-witness-3): the in-circuit length IV (count*2^64) is an unconstrained witness that can diverge from a len-based non-circuit consumer, but it yields no independent false-acceptance — the forging power comes entirely from the unsigned-commitment hole (confirmed above), and in the only regime where length-binding would matter (a checked signed commitment) Poseidon2's length-bearing IV gives domain separation/collision resistance. Guard cited: hashes.nr:30-32 + poseidon2 v0.3.0 length IV (verified by poseidon2.rs hash_is_deterministic_and_length_separated). Listed as hardening (bind true count into the signed object).
- Malformed proof_hex panic (verifier-malformed-proofhex-panic-4): confirmed to panic (reproduced: "zz", "abc", short blob, oversized length prefix all panic at verifier.rs hex_decode/take_lp before bb), but it is a liveness/DoS issue, never a false-accept (verify_manifest cannot be made to return Ok via this path), and no in-process verifier service exists in-tree (verify_manifest is called only from tests). Guard cited: the panic never yields Ok(()), and verifier.rs:200-201 already rejects empty proof_hex. Listed as hardening (route through CheckError).
- Circuit-id r-bucket slack (circuit-id-r-bucket-slack-3) and n/d trust (verifier-declared-n-trusted-5) as STANDALONE forgeries: an r=8 proof relabels to r=4 and an n=64 proof relabels to n=16, but row activity is gated by row_count (not R) throughout scan.nr and the commitment is N-invariant (commit_fold IV is count, not N), so the disclosed result is unchanged — the relabel attests the same statement. Guard cited: scan.nr:52/70/104 (row_count gates activity), hashes.nr:30-32 (count-bearing IV). The relabel only becomes a forgery as a force-multiplier on the vk/public-input gaps; consolidated into the confirmed 'trusts declared n/d/r' HIGH issue whose fix is the vk-pinning + public-input reconstruction.
- nargo-execute false-success gotcha: handled correctly on the prover side (driver.gen_witness treats witness-file absence as unsat), but this is a prover-side concern the adversary controls anyway and gives NO verifier-side assurance. Not a verifier soundness issue; the real soundness gate must be bb verify on an honest vk/public-inputs, which the two catastrophic gaps currently bypass. A reviewer must not mistake the witness-absence guard for a verifier soundness check.

## Full synthesis

# ZK Prover/Verifier Soundness Audit — Final Report (v1, sparq-zk / sparq-zk-compose)

## Summary & Assurance

**Bottom line: v1 verifier soundness is broken. `verify_manifest` proves essentially nothing to a relying party.** It is an honest research scaffold of the *in-circuit relations* — the scan completeness/soundness relation (`scan.nr`) and the integer/float filter comparison relations (`filter_int.nr`/`filter_float.nr`) are correctly constrained in-circuit — but the verifier-side *binding layer* that would make those relations mean anything to a third party does not exist yet. A prover that controls its own side (the threat model) can make the verifier return `Ok(())` over arbitrary false query results, replay any captured manifest forever, and attest facts from credentials no issuer ever signed.

The verifier's actual structure is three disjoint checks that never meet:

- **Stages 1a–1b–2** (`verifier.rs:129-188`, `verify.rs`): re-parse the query, re-derive circuit ids, and check binding-edge equalities — all over the **prover-declared ProofInputs JSON**.
- **Stage 3** (`verifier.rs:199-219`, `driver.rs:181-203`): hand the **prover-supplied `(proof, public_inputs, vk)`** triple, decoded verbatim from `proof_hex`, to `bb verify`.

Stages 1–2 check a JSON statement; Stage 3 checks a detached cryptographic proof over a *different*, prover-chosen public-input vector under a *prover-chosen* verification key. **Nothing checks that the two describe the same statement, and nothing ties either to a canonical circuit, an issuer signature, or a fresh challenge.**

I verified the load-bearing claims directly against the code on `main` (`verifier.rs`, `verify.rs`, `driver.rs`, `build.rs`). The verifier path is short and unambiguous; the gaps below are confirmed in source, not inferred. **Do not present v1 as proving anything to a relying party.** This is a credential system — the appropriate posture is that the cryptographic acceptance gate is not yet sound.

## Confirmed Issues

### 1. (CRITICAL) bb-verified `public_inputs` are never reconstructed from or compared to the declared statement
**Location:** `crates/sparq-zk-compose/src/verifier.rs` `verify_manifest` (199-219), `decode_artifacts` (234-242).

`decode_artifacts` splits the prover-controlled `sp.proof_hex` into `(proof, public_inputs, vk)` and passes `public_inputs` straight to `bb verify -i`. The verifier never serializes the public-input field vector from the declared `commitments / pattern_* / rows / row_count / operand_enc / op / bound / expected` (+ its own challenge) in `main` declaration order and asserts byte-equality with `art.public_inputs`. An adversary generates an *honest* bb proof over any small true statement it legitimately holds (no malicious circuit required), then writes a false `ProofInputs::Scan` into the manifest while leaving `proof_hex` pointing at the honest proof; `derive_id` still passes if k/r buckets match (trivially tuned). **Forges arbitrary results.** This is the single load-bearing missing check.

**Fix:** Before/independent of `bb verify`, reconstruct the public-input byte vector from the declared ProofInputs using the verifier's *own fresh challenge*, and assert byte-equality with `art.public_inputs`. Reject on mismatch.

### 2. (CRITICAL) `bb verify` uses the prover-supplied verification key
**Location:** `verifier.rs` (199-219, 234-242); `driver.rs` `verify` (181-203) writes `art.vk` and runs `bb verify ... -k <prover_vk>`.

The verifier never recomputes the vk from the compiled circuit member named by the re-derived `CircuitId`, never loads a pinned/content-addressed vk, and `verify()` takes no `CircuitId` at all. The comment at `verifier.rs:204-209` ("we recompute the vk from the compiled member") is false — the only `--write_vk`/compile calls are in `driver.rs::prove`. An adversary compiles a trivial circuit with the right public-input arity but no constraints, `bb prove --write_vk` over fabricated inputs, bundles the attacker vk, and `bb verify` accepts. Even with #1 fixed, an attacker-chosen vk defeats the whole cryptographic gate.

**Fix:** Recompute (or load from a trusted content-addressed store keyed by the full re-derived `CircuitId`) the canonical member's vk and use *that* for `bb verify` — never the prover-supplied vk.

### 3. (CRITICAL) No issuer-signature / key-set check: unsigned prover-chosen commitments
**Location:** `crates/sparq-zk/src/commit.rs` (no signature); `verifier.rs` `verify_manifest` (no registry/signature cross-check); `registry.rs` (issuerKey recorded as an IRI only); `scan.nr` step 1.

`C(G)` is `poseidon2::hash` over prover-supplied leaves under any salt, with no signature. The scan circuit only proves `commit_fold(witnessed_leaves, count) == commitments[g]` for a prover-supplied `commitments[g]`. The verifier never reads the registry, verifies a signature, or compares `commitments[]` to any attested value; `manifest.rs` documents this as deferred. Spec clause S(a) is wholly unimplemented. A prover commits to any triple set it invents, or to a strict subset of a genuine credential — **drop the suspension triple, recompute `C` over the truncated leaves, prove** — exactly the headline suppression the spec claims to prevent. The prover is effectively the issuer of every fact it proves. (Works with the honest circuit/vk/public inputs, so it is independent of #1/#2.)

**Fix:** Verify `Sign(pk_i, C(G_i))` with `pk_i` in the disclosed key-set K — in-circuit (preferred) or at minimum verifier-side before acceptance. `commitments[]` must never be an unsigned prover-chosen public input.

### 4. (CRITICAL) No replay/freshness binding: every manifest is infinitely replayable
**Location:** `verifier.rs` `verify_manifest` (no nonce param; never reads `manifest.binding`); `zk/compose/*/src/main.nr` `let _ = challenge`; `manifest.rs` `BindingMode`.

`verify_manifest` takes no verifier nonce, never compares the proof's challenge to a fresh value, and never tracks single-use. `manifest.binding.challenge()` has **zero call sites** in the verifier. Every stage is a deterministic function of the manifest bytes, so a captured manifest verifies forever, across sessions and relying parties. Worse, the *obvious* hardening patch (`binding.challenge() == N`) is also defeated: the JSON challenge is decoupled from the challenge committed inside `art.public_inputs`, so a single JSON string substitution forges freshness with no re-proving.

**Fix:** Accept a verifier-issued fresh nonce, inject it as the challenge in the reconstructed public-input vector (per #1) and assert it equals the proof's challenge bytes, and enforce single-use.

### 5. (CRITICAL) FILTER operator/bound/verdict never bound to the query's FILTER expression
**Location:** `verifier.rs` `derive_id` (113-123, `let _ = bound;`); `verify.rs` `expression_has_exists` (159-184).

The verifier re-parses the query only to extract BGP patterns and reject EXISTS; FILTER comparison nodes are walked solely to look for EXISTS and otherwise discarded. `derive_id` throws away `bound` and never reads `op`/`expected`. A credential with `age = 17` against `FILTER(?age >= 18)` (honest verdict: drop) is proven by a `filter_int` sub-proof over `op=Ge, bound=17, expected=true` — `17 >= 17` is genuinely true, a satisfiable instance of the same circuit family. The binding-edge equality holds, bb verifies the true instance, and the relying party reading `>= 18` plus a non-empty result concludes `age >= 18`. **False, accepted.** Independent of #1/#2 (each sub-proof is honest).

**Fix:** Parse the FILTER into `(variable, operator, constant)`; require a matching `FilterInt` sub-proof whose `op`/`bound` equal the query's, whose operand variable maps to the constrained scanned slot, and whose `expected` gates row inclusion. Fold `op/bound/expected` into the bound public-input vector.

### 6. (HIGH) Binding edge ignores which slot the FILTER constrains and never prunes by verdict
**Location:** `verifier.rs` stage 2 (161-185); `verify.rs` (no FILTER-variable→slot mapping).

Stage 2 only asserts `scan.rows[from_row][from_slot] == filter.operand_enc` over declared JSON. Nothing checks `from_slot` is the FILTER's operand column, nor that `expected==false` rows are excluded. For `FILTER(?age >= 65)` the prover points the edge at a *salary* slot whose value satisfies `(Ge, 65)`; equality passes, bb verifies `70000 >= 65`, and rows with real failing ages are presented as passing. Independent of #1/#2.

**Fix:** Derive the `(pattern, slot)` the FILTER variable binds to and require the edge to reference exactly that slot; gate row inclusion on the verdict.

### 7. (HIGH) Composition seam (operand substitution / kind confusion) is JSON-only
**Location:** `verifier.rs` stage 2 (161-185) and `derive_id` (95-125).

The "scanned column equals filter operand" seam is a `FieldHex` string equality over two prover-written JSON fields; the kind dispatch is an enum-tag check on the JSON, not the attached proofs. Because public inputs are unbound (#1), a prover declares `rows[r][slot]=O` and `operand_enc=O` while attaching a genuine filter proof generated over a *different* operand `O'`. The two cryptographic pieces are never linked.

**Fix:** Fold `operand_enc` into the byte-compared public-input vectors of both the scan and filter proofs (subsumed by fixing #1 + #6).

### 8. (CRITICAL) Cross-graph bnode join guard is driven by prover-declared, proof-unbound attributions
**Location:** `verify.rs` `cross_graph_join_obligations` (248) + `recheck` (269-282); `verifier.rs` (133-146, attributions taken verbatim); `scan.nr` (no per-row graph attribution in-circuit).

The Q6 obligation decision is made purely from `manifest.attributions`, never cross-checked against any proof-bound quantity. The scan circuit binds no per-row source graph (a row need only occur in *some* slot of *some* graph), so an honest proof cannot refute a false attribution. A prover whose data joins a bnode-valued variable across two distinct graphs declares both joined patterns from the *same* single graph (`attributions=[[0],[0]]`); `|{0}|=1`, `cross_possible=false`, `recheck` returns `Ok([])`, and the forbidden cross-graph bnode correlation is admitted — directly contradicting the module-doc safety claim (`verify.rs:20-23`). The honest prover-side `bnode_guard` (`trace.rs`) is adversary-controlled and never re-run. Independent of #1/#2 (attributions are not public inputs).

**Fix:** Bind per-row source-graph attribution in-circuit, surface it as a public input, and reconstruct+compare against `manifest.attributions`.

### 9. (HIGH) Cross-graph bnode salt-separation has no in-circuit or verifier enforcement
**Location:** `encode.rs` `encode_term` (56-59, salt off-circuit); `build.rs` `build_scan` (salt off-circuit); `scan.nr` (salt never in-circuit); `registry.rs` (no salt-uniqueness check).

The Q6 "bnodes are distinct by construction" guarantee rests on distinct per-graph salts, but the salt never enters any circuit and the verifier never sees or compares salts. No production OS-random salt ingest exists. An adversary-ingester commits two graphs under the same salt, so a same-label bnode encodes identically across both commitments — a cross-graph correlation handle. A privacy/merge-distinctness break (not result forgery) under the adversary-as-ingester model the threat map grants.

**Fix:** Enforce globally-unique per-graph salts at a trusted ingest and bind the salt under the issuer signature, or bind the salt into the in-circuit attribution check.

### 10. (HIGH) Query text not bound into the proof: FILTER-add / constant-swap replay
**Location:** `verifier.rs` stage 1a (132-146); `verify.rs` `collect_patterns` (121-156, projection and FILTER expr discarded).

The query lives only in `manifest.query`, checked only by `recheck` (fragment/bnode/arity); the scan public inputs carry no query digest. `collect_patterns` discards the projection list and the FILTER expression. An honest scan-only manifest for `{ ?s <ex/age> ?o }` is accepted under `... FILTER(?o >= 100)` (the disclosed unfiltered rows are read as satisfying `>= 100`), and a constant swap presents an age scan as a salary answer. (Projection-narrowing and FILTER-drop stay true and are not breaks; FILTER-add/change and constant-swap are the forgeries.)

**Fix:** Fold a canonical query digest into the bound public-input vector and cross-check query BGP constants against `pattern_const_enc` and query FILTERs against required filter sub-proofs.

### 11. (HIGH) Circuit-id re-derivation trusts declared n (and d); r-bucket relabel slack
**Location:** `verifier.rs` `derive_id` (95-125); `build.rs` `derive_scan_id`/`derive_filter_int_id` (31-44).

`derive_id` re-derives only k and the r bucket and reads `declared_n` straight from the declared id; `smallest_bucket([16,64], declared_n)` round-trips any compiled bucket, so `derived.n == declared.n` tautologically. The r bucket comes from the disclosed active-row count, not the producing circuit. The S2.4 "re-derive the circuit id from the public statement" rule is unmet on the n/d/r axes. Standalone the relabel is bucket-invariant (the commitment IV is `count`, not `N`), so it attests the same statement; combined with #1/#2 it lets the attacker freely choose the advertised bucket.

**Fix:** Pin the vk per full `CircuitId` and reconstruct the public-input layout for the declared `n` (fixing #1/#2 subsumes this). `n` cannot be re-derived from public data, so vk-selection + public-input layout is the only sound route.

### 12. (MEDIUM) Revocation unimplemented; status-list index disclosed in the clear
**Location:** `manifest.rs` `RevocationStatus`; `verifier.rs` (ignores `revocation`).

No revocation/non-revocation check, no in-circuit status-list inclusion + bit-unset proof, no freshness-window check. A suspended/revoked credential still verifies, and the clear index is a linkability channel. The feature is simply absent.

**Fix:** Implement S2.6 (hidden-index status-list inclusion + bit-unset, bound to a disclosed list version, with a verifier freshness-window check).

## Hardening (defense-in-depth, not strictly breaks)

- **Reject malformed `proof_hex` instead of panicking.** `hex_decode` (`verifier.rs:263-268`) panics via `.expect("valid hex")` / OOB slice on non-hex or odd-length input; `take_lp` (249-253) panics on a `<4`-byte buffer or an oversized length prefix — all prover-controlled, all before any bb call. It is a DoS, not a false-accept (release profile is `panic="abort"`), but make both return `Result` and add a `CheckError::MalformedProof` variant, mirroring the existing empty-`proof_hex` `MissingProof` guard.
- **Constrain / document `row_count` semantics.** It is an unconstrained-`<=R` set-cardinality over the RDF-merge union, not an occurrence count; the verifier uses it only to size the r bucket. Correct under documented union semantics, but document loudly so a relying party never reads it as "number of credentials."
- **Normalize literal lexical forms** (or reject non-canonical/signed `xsd:integer`) before encoding: `filter_int.nr` can only bind a canonical non-negative decimal token, so a committed `"007"`/`"-5"` is unbindable and (with the missing FILTER-coverage gate) freely kept/dropped.
- **Bind the true triple count** into the signed commitment object once issuer signatures land, so an unconstrained in-circuit `counts[g]` cannot present a short-count view of a long credential.
- **Add negative e2e tests** for every binding gate once implemented: mismatched-statement proof → REJECT; prover-supplied vk → REJECT; replayed manifest under a fresh nonce → REJECT; `attributions=[[0],[0]]` cross-graph bnode join → REJECT. The current suite covers only happy-path + an r-tamper id-mismatch + an honestly-declared `[[0],[1]]` rejection.
- **Fix the false-assurance comments** (`verifier.rs:204-209`, `scan.nr` replay note, `verify.rs:20-23`) — they assert guarantees the code does not deliver.
- **Gate `HolderPop`** behind an explicit "unimplemented" error until holder-key PoP exists; today it carries a `holder` IRI but performs zero proof-of-possession and the verifier never reads it.

## Attacks Considered & Refuted / Guarded (assurance evidence)

These attacks were examined and do **not** constitute independent breaks; the cited guard or scoping is the assurance:

- **Salt-collision smuggling a cross-graph bnode join past the obligation gate** — refuted as an *independent* break: the gate (`verify.rs cross_graph_join_obligations:248`) is value-blind and **salt-independent**; it flags any `|A_i ∪ A_j| > 1` join lacking a declared obligation. The only bypass is an attribution lie (the confirmed Issue 8), which is salt-agnostic. The unbound-salt *privacy* gap is confirmed separately (Issue 9).
- **Vacuous non-bnode obligation** — refuted in its own scenario: with honest distinct per-graph salts, bnode encodings are unequal by construction (**guard: `encode.rs:56-58` salt-separation, verified by the `commit.rs salt_separation` test**), so no correlated row is produced. Real correlation requires salt reuse (Issue 9) or an attribution lie (Issue 8).
- **`row_count` set-vs-multiset deduplication** — refuted: under the system's declared RDF-merge/union semantics the deduplicated set-count is the correct answer (**guard: `scan.nr:14-17` "complete w.r.t. the union", `encode.rs:14` "exactly RDF merge semantics"**); the verifier never reads `row_count` as an occurrence count (`verifier.rs:110` `let _ = row_count`).
- **`commit_fold` count unconstrained** — refuted as an independent forgery: yields no false-acceptance beyond the unsigned-commitment hole, and the length-bearing Poseidon2 IV gives collision resistance across lengths (**guard: `hashes.nr:30-32` + poseidon2 v0.3.0 length IV, verified by `poseidon2.rs hash_is_deterministic_and_length_separated`**).
- **Malformed `proof_hex` panic** — refuted as a soundness break: it crashes, never returns `Ok(())` (**guard: panic never yields acceptance; `verifier.rs:200-201` already rejects empty `proof_hex`**); no in-process verifier service exists in-tree. Listed as hardening.
- **Circuit-id r-bucket / n-d relabel as standalone forgeries** — refuted standalone: row activity is gated by `row_count`, not `R`, and the commitment is `N`-invariant (IV is `count`), so the relabel attests the same statement (**guard: `scan.nr:52/70/104`, `hashes.nr:30-32`**). It bites only as a force-multiplier on #1/#2; consolidated into Issue 11.
- **nargo-execute false-success gotcha** — not a verifier issue: handled prover-side (witness-absence = unsat), but prover-side is adversary-controlled and gives no verifier assurance. A reviewer must not mistake this guard for a soundness check.

Confirmed-but-not-independent findings whose harm is fully delivered by a stronger confirmed issue (and thus folded into the fixes above): salt-unbound-forge / scan-attribution variants → Issues 8–9; circuit-id-r-bucket / n-downgrade → Issue 11; challenge-rebind → Issue 4.

## Methodology

I consolidated a fan-out of per-finding adversarial verdicts (each finding judged independently by an exploit-builder and a guard-finder) against a structured threat map, then re-verified every load-bearing claim directly against the merged code on `main`. I read in full the two files the entire verdict set pivots on — `crates/sparq-zk-compose/src/verifier.rs` (the four-stage verifier, `decode_artifacts`, `hex_decode`/`take_lp`) and `crates/sparq-zk/src/verify.rs` (`recheck`, `cross_graph_join_obligations`, `collect_patterns`, `expression_has_exists`) — plus the corroborating `driver.rs verify` (181-203, confirming `art.vk`/`art.public_inputs` are passed verbatim to `bb verify` with no `CircuitId`) and `build.rs derive_scan_id` (31-38, confirming declared `n` round-trips).

A finding was promoted to a **confirmed issue** when the code supported it and either both stances agreed it was exploitable, or the disagreement resolved in favour of exploitability after weighing the cited guard (a guard-finder's `confirmed_exploitable` with no `guard_found`, corroborated by an exploit-builder reproduction, is strong evidence of a real break). Where stances split between `confirmed_exploitable` and `confirmed_weakness_not_exploitable`, I sided with the analysis grounded in code and against any "exploit" that merely renames a missing feature — except where the missing feature is itself a confirmed gap against the system's intended (credential-system) guarantee, in which case I report it as a confirmed issue at its true severity (Issues 3, 9, 12). Attacks were **refuted/guarded** only when a concrete guard in the code defeats them or when they are strictly dominated by and reducible to an already-confirmed issue; the guard or dominating issue is cited as assurance. I prioritized empirical honesty over reassurance throughout: this is a credential system, and the verifier's cryptographic acceptance gate is not yet sound.
