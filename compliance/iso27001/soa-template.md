# ISO/IEC 27001:2022 — Statement of Applicability (SoA) template + ISMS scaffold

> **THIS IS A TEMPLATE, NOT A CERTIFICATE.** It is provided for an **adopting organization**
> to populate, decide, and sign as part of operating its own ISMS. Nothing here is a passed
> control, a management decision, or an accredited audit result. The *applicability +
> technical-evidence* columns are pre-filled from [`controls.md`](./controls.md) to save the
> organization work; the **decision, justification-of-exclusion, and sign-off columns are
> left blank for the org to complete.** Remediates gap **GAP-ISO-1**.

## How to use this

ISO/IEC 27001 clause 6.1.3(d) requires a **Statement of Applicability** that, for every
Annex A control, records: (a) whether it is **applicable**, (b) the **justification** for
inclusion or exclusion, (c) the **implementation status**, and (d) a pointer to the
**control/evidence**. [`controls.md`](./controls.md) already supplies (a), (c), and (d) for
sparq-as-a-product. The adopting organization:

1. Imports the `controls.md` rows as the SoA's applicability + evidence columns.
2. For each **N/A(operator)** control, replaces "operator-owned" with *the org's own*
   implementation in *its* deployment (these become applicable+implemented in the org's SoA).
3. For each **AUDIT-READY** control, performs the organizational act (signs the policy, runs
   the risk-treatment decision, schedules the management review) and records it.
4. Justifies any *excluded* control under clause 6.1.3(d).
5. Has top management approve and sign (clause 5.1 leadership).

## ISMS clauses 4–10 scaffold (what an org must additionally produce)

These are the management-system clauses that **no repo artifact can be** — listed so the
org knows the remaining work beyond the Annex A controls.

| Clause | Artifact the org must produce | sparq input the org can reuse |
|---|---|---|
| **4** Context | ISMS scope statement; interested parties | This product mapping + `research/threat-model.md` scope |
| **5** Leadership | Signed information-security policy; roles/responsibilities | `SECURITY.md`, `CODEOWNERS`, `docs/branch-protection.md` as input |
| **6** Planning | Risk assessment + risk-treatment plan; **SoA** (above); security objectives | `research/threat-model.md` (assets, boundaries, STRIDE) seeds the risk register; `controls.md` seeds the SoA |
| **7** Support | Resources, competence, awareness, documented-info control | `CONTRIBUTING.md` + `AGENTS.md` as the awareness/competence baseline |
| **8** Operation | Operational planning + risk-treatment implementation | The CI gate stack is the operational control evidence |
| **9** Performance evaluation | Monitoring/measurement; **internal audit**; **management review** | CI dashboards, Scorecard, advisory watchdog as monitoring inputs; the audit/review are org acts |
| **10** Improvement | Nonconformity + corrective action; continual improvement | GHSA advisories, the beads tracker, the conformance ratchets as the improvement loop |

## Companion policy templates (also gap GAP-ISO-1)

Cross-framework policy templates an org would adopt (vulnerability-management/CRA
disclosure, secure-SDLC, dependency, release-signing) are intended to live under the
shared `compliance/policies/` directory and are owned across the `cra` / `ssdf` / `sbom` /
`slsa` framework worktrees (to avoid duplication). This ISO 27001 SoA template references
them; it does not duplicate them. Where they are not yet present, that is part of the
respective framework's remediation, not a separate ISO 27001 gap.

## Honesty footer

Populating this template does **not** make sparq "ISO 27001 certified." Certification is an
**accredited certification body's** Stage 1 + Stage 2 audit of an **operating ISMS over
time**. This template is the head start; the certificate is external by definition.
